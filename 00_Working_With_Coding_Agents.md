# Working With Claude Code and Codex on These Projects

This file is the shared operating procedure. The three project files apply it. Read this once; the project files assume it.

---

## 1. The split, as a rule

**You do the work that requires judgment, credentials, a body, or a signature.**
- Domain decisions: rubric dimensions, scoring rule tables, persona designs, sequence strategies, thresholds, what is in and out of scope
- Anything that touches a real account: Twilio numbers, API keys, ngrok, Resend/SendGrid domain setup, WhatsApp sandbox join, GitHub repo creation, secrets
- Anything that requires the physical world: making test calls, recording role-plays, receiving SMS on your phone, listening to audio
- Anything that requires blind human labeling: hand-rating transcripts, labeling leads, reviewing synthetic data for realism
- Review and verification of everything the agent produces, especially numbers
- Writing the honesty-critical parts of the README (eval results, limitations, what production needs) from actual run output
- Loom recording, release tagging, outreach

**The agent does the work that is specified, testable, and repetitive.**
- Scaffolding, boilerplate, config, Docker, migrations
- Adapters to vendor SDKs (Twilio, Deepgram, Cartesia, Resend, LangGraph) against a spec you give it
- Data models and repositories
- Test suites, including tests for behavior you describe in plain English
- Harness runners, metrics code, comparison scripts, dashboards
- Synthetic data generators, given the spec format you designed
- Debugging when you paste logs and describe what you observed
- First drafts of docs that you then edit

**Neither of you fabricates results.** The agent never writes a number into a README that did not come from a run it executed in that session. You never paste a number you did not see in run output. This is the same standard as your resume work and it is the standard reviewers will apply to a repo.

## 2. Session structure

Each agent session is one task with one acceptance criterion. Do not ask for "week 1." Ask for "the Twilio WebSocket handler that passes the echo test."

For every task:
1. **Plan first.** Start in plan mode (Claude Code: `/plan` or ask it to propose a plan before touching files; Codex: ask for a plan in the first message). Read the plan. Correct it. Only then let it write.
2. **State the acceptance criterion up front.** "Done means `pytest tests/test_scoring.py` passes and the rule table in the docstring matches `docs/scoring.md`."
3. **Tell it what not to touch.** Prompt files, the rule table, the persona YAMLs, anything you authored.
4. **Have it run the tests and show you the output.** Not "tests pass." The output.
5. **Review the diff yourself** before committing. Read every file it created. If you cannot explain a file, you cannot demo it.
6. **Commit with your own message.** One task, one commit, on a branch. Merge when reviewed.

Keep sessions short. A session that has been going for two hours and has touched fifteen files is a session where you have lost track of what the agent did.

## 3. The project instruction file

Claude Code reads `CLAUDE.md` at the repo root. Codex reads `AGENTS.md`. Put the same content in both (or symlink). Each project file below gives you the content. The shared rules that go in every one:

```
## Rules for this repo

- Never hardcode secrets. All credentials come from environment variables via config.py. .env is gitignored.
- Never write numbers into README.md or docs/eval_results.md. Those are generated by scripts or entered by the owner from run output.
- Do not modify files under prompts/, personas/, sequences/, or docs/scoring_guide.md unless the task explicitly says to. These are owner-authored.
- Every new module gets a test. Run the full test suite before declaring a task complete and paste the output.
- Prefer small, pure functions. Scoring, classification thresholds, and routing decisions must be deterministic and unit-tested.
- No em-dashes in any prose or docs. Use commas, colons, or periods.
- Log with structured logging and redact phone numbers, emails, and names. Never log raw transcript text at INFO level.
- When you are unsure about a vendor API detail, say so and stub it behind an interface rather than guessing. Do not invent SDK method names.
- Do not add dependencies without listing them and why in your summary.
- Python 3.11+, type hints on all public functions, ruff for lint, pytest for tests.
```

## 4. How to write a task prompt

Template:

```
Task: <one sentence>

Context: <which module, what exists already, what this connects to>

Spec:
- <bullet list of behavior, be concrete>
- <interfaces to implement, with function signatures if you have them>

Constraints:
- <files not to touch>
- <libraries to use or avoid>

Done means:
- <test or command and its expected output>
- <what to show me>

Start by proposing a plan. Do not write code until I confirm.
```

Give it the relevant section of the scope document. Paste the data model, the node list, the metric definitions. The agent works much better from your spec than from a description of your spec.

## 5. What to do when it goes wrong

- **It guessed an API.** Stop. Ask it to show you the documentation source or to stub behind an interface. Vendor SDKs (Twilio Media Streams, Deepgram streaming, Cartesia) are exactly where agents hallucinate parameter names. Verify against the vendor docs yourself for these three.
- **It rewrote something you authored.** Revert that file. Add it to the do-not-touch list in CLAUDE.md.
- **It claims tests pass without output.** Ask for the output. If the output is not there, run the tests yourself.
- **It added a fake number to a doc.** Remove it, and add the rule to CLAUDE.md if it is not already there.
- **It is going in circles on a bug.** Stop the session. Reproduce the bug yourself, add logging, paste the logs into a fresh session with a narrow question.
- **Concurrency and cancellation bugs (ArcAgent barge-in especially).** Agents write plausible async code that has races. Ask for the state machine in words before the code, and ask it to write the test that exercises the race first.

## 6. Codex vs Claude Code

Use whichever you prefer. Practical differences that matter here:
- Both read a root instruction file (`CLAUDE.md` / `AGENTS.md`). Keep them identical.
- Claude Code plan mode is useful for the orchestration and telephony tasks where a wrong design costs a day. Use it there.
- For long-running local commands (ngrok, the scheduler loop, Streamlit), run them in your own terminal, not inside the agent session. The agent should write the code and the run instructions; you run the services.
- Neither can make a phone call, receive an SMS, or listen to audio. Every task that ends in "and verify on a real call" ends with you.

---

## 7. Time expectations

The agent does not make the three-week plans shorter by much. It makes them survivable. Expect the split to be roughly: agent writes 70 percent of the code, you write 100 percent of the domain artifacts and spend most of your hours on review, real-world testing, labeling, and documentation. If you find yourself spending most of your time prompting and little time reviewing, you are moving too fast and the repo will show it.
